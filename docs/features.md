## Food `/food`

- Meal logs + macros, AI meal-photo scanner, quick-add search (matches menu item OR restaurant name via widened `/menu-items/search`, results grouped by restaurant, meal-type picker).
- **Chain-restaurant search** (Spoonacular direct API, `artifacts/api-server/src/lib/spoonacular.ts`): explicit-submit "Search chains" surfaces REAL published nutrition for national/regional chains (web + mobile) with one-tap log via the shared log hook. Two-call shape (GET `/chain-menu-items/search` returns id/name/restaurant/image, no macros → GET `/chain-menu-items/:id` returns clamped macros; search registered before `:id`). Untrusted upstream Zod-validated/clamped/sanitized, https-only images; layered quota defense = one combined per-user hourly limiter on BOTH routes + module global daily budget (ET reset, counts real calls only) + 1h caches; coarse 503 (no_key/budget/timeout/upstream) + 404 not-found; key from `SPOONACULAR_API_KEY`, never logged. Premium-gated, not requirePatient (staff self-track).
- **Barcode scanner** (2026-07): GET `/barcode-products/:barcode` (6-14 digits) → Open Food Facts (`artifacts/api-server/src/lib/openfoodfacts.ts`: Zod-validated/clamped untrusted upstream, 24h cache, 8s timeout, UPC-12 leading-zero retry, kJ→kcal + salt→sodium fallbacks, implausible sodium >8g → null, no-energy → 404; 60/hr per-user limiter, coarse 404/503, https-only images, User-Agent per OFF policy). Web: `barcode-scanner-dialog.tsx` (@zxing/browser camera + always-available manual number entry) from Food Quick Add card; Mobile: `components/track/BarcodeScanCard.tsx` (expo-camera CameraView native-only, manual entry on Expo web). Per-serving vs per-100g basis labeled in both UIs; logs via shared log-menu-item hooks (which pass through optional `servingSize`).

## Restaurants (Dining Out Guide)

- 18 curated local chains, each with a full baked-in menu (~26-29 items; generated by `scripts/src/gen-menus.ts` → `lib/db/src/restaurant-menu-extra.ts` as `RESTAURANT_MENU_EXTRA`, merged in `seedRestaurants` curated-first with case-insensitive within-seed dedupe + exact-name DB idempotency, so prod picks them up on startup), healthy-pick tips (staff-editable), "Log to food diary" buttons on menu items (web + mobile via shared `use-log-menu-item` hook). Nutrition refreshed against chains' PUBLISHED values (2026-07): 281/~430 items carry web-grounded published nutrition via `scripts/src/enrich-menus.ts` (gpt-5.4 + web_search, grounding-verified, 0.4×–2.5× calorie plausibility guard; remainder keep AI estimates — mostly custom builds chains don't publish); existing DB rows updated by the version-gated `syncMenuNutrition` (`app_settings.menu_nutrition_version` vs `MENU_NUTRITION_VERSION` in seed-data.ts) — bump the constant after re-running enrichment; only the 8 nutrition columns sync, names/tips never.
- Patient-added restaurants: `restaurants.owner_user_id` NULL = curated; owned rows are patient-private — every restaurant/menu route filters `(ownerUserId IS NULL OR = me)`, admin restaurant/menu CRUD requires `ownerUserId IS NULL`, never expose ownerUserId, Restaurant schema has required `isMine`.
- POST /restaurants/custom (requirePatient, 5/day in-memory limit, 30/user cap, partial unique index on (owner, lower(name)), optional `location` input) generates a web-grounded menu: single openai.responses.create call (gpt-5.4 + web_search tool, web pages marked data-not-instructions) pulls REAL dish names, falls back to non-grounded chat.completions "typical menu" on any failure; nutrition always AI-estimated; `restaurants.menu_source` stores bare source domain (cleanDomain regex, stripLinks on all AI text) shown as "Dish names from <domain>" on web+mobile; Zod-validated, clamped, "looksLikeRestaurant" gate, AI-estimate disclaimers in UI.
- Patients edit their OWN restaurant menus (web UI only): POST /restaurants/:id/menu-items, PATCH+DELETE /menu-items/:id — requirePatient, ownership-bound, uniform 404s, 40-item cap FOR UPDATE in transaction. DELETE /restaurants/:id owner-only.
- "Order on DoorDash" deep-links (`doordash.com/search/store/<name>` — no public ordering API, hand-off only) on web + mobile.

## Activity & Sleep `/activity` (2026-07)

- Manual activity/sleep logging (10 pts each, manual-only, dedupe `activity_log:<date>`/`sleep_log:<date>`), 7/30-day charts (`days` query param is NUMERIC enum 7|30), streak.
- Device pairing in `device_connections`: **Oura ring** via personal access token (plaintext in DB by design, only `tokenLast4` ever returned/logged; connect validates token live, sync pulls daily_activity + long_sleep sessions + daily_sleep score, upserts `onConflictDoUpdate` on partial unique (userId, source, externalId) so re-syncs refresh values; per-connection toggles syncActivity/syncSleep; disconnect optionally removes synced rows via `?removeData`; rate limits connect 5/hr, sync 4/hr, in-memory).
- **Phone steps** (mobile iOS only): expo-sensors Pedometer 7-day read → preview → import as source 'phone' (externalId `phone:<date>`); Android/web get honest "not available" copy. **Apple Health**: info-only card — needs App Store build, no fake toggle.
- Nightly Oura sync cron 6:00 ET (`activityScheduler.ts`, sequential, per-user try/catch). Synced rows are NOT deletable via API (DELETE manual-only → 404).
- Routes patient-only + premium-gated; morning briefing includes yesterday's active minutes/steps + last night's sleep. Mobile: Track tab 5th segment "Move" (`components/track/MoveTab.tsx`).

## Retention features (2026-07)

- **Wellness Streak** (Home card): GET /streak counts consecutive days with any qualifying log (food, weight, glow, mind, activity), computed live from distinct log dates — no streak table. Grace: today not yet counted doesn't break the streak. Once-ever milestones (7/14/30/60/100 days → 50/75/150/300/500 pts) awarded via reward_events dedupe `streak:<days>` (survives streak resets). Response includes current, longest, todayCounted, nextMilestone.
- **My Journey `/journey`**: GET /journey read-only recap timeline — weight trend, milestones, monthly summaries, progress photo references. Patient-private.
- **Weekly Report `/weekly-report`**: GET /weekly-report lazily generates an AI recap of LAST week (Mon-Sun ET) on first request, cached in `weekly_reports` (unique user+week, onConflictDoNothing, per-user in-flight map). Wins/focus/encouragement from the patient's own stats; educational-only language.
- **Monthly community challenges** (Community page section): `challenges` + `challenge_participants` tables; lazy ensureChallenges seeds current+next month from a rotating template list (log_days/meals/glow_checkins/weigh_ins/move metrics). GET /community/challenges + POST /community/challenges/:id/join. Progress computed from the user's OWN logs only — only aggregate participant/completion counts shared ("only you can see this" copy). Completion awards 150 pts, dedupe `challenge:<key>:<month>`.
- **Meal Plan `/meal-plan`**: GET /meal-plan/current + POST /meal-plan/generate. AI 7-day plan (Grok 4.5 json_object, 60s timeout, Zod-validated: exactly 7 days, calories clamped 0-2500, 1-12 grocery categories, dates assigned server-side) from goal facts + 30 distinct recent food names in a `<patient_data>` data-not-instructions block. Stored in `meal_plans` (jsonb content, unique user+week). Max 2 generations per ET week — generation AND upsert share one in-flight promise per user (double-tap burns one generation), setWhere generations<2 race-loss → 429 ("fresh plan unlocks Monday"), AI failure → 503 and never burns quota. Patient-private, premium-gated, disclaimer footer.

## Workouts `/workouts` (2026-07)

- Fitbod-style training suite, routes in `routes/workouts.ts`, schema in `lib/db/src/schema/workouts.ts` (5 tables: `exercises`, `workouts`, `workout_exercises`, `workout_sets`, `workout_preferences`). Premium-gated + requireAuth (NOT patient-only — staff may self-track). All data user_id-scoped, patient-private.
- **Exercise library**: 99 seeded exercises (14 muscle groups, 7 equipment types, difficulty levels, instructions, primary + secondary muscles). GET /exercises; seeded idempotently via `seedExercises` (also runs in prod self-seed).
- **Workouts CRUD**: create (date + title), list (exercise/set counts), detail, delete; add/remove exercises; log/delete sets (reps + optional weightLbs). POST /workouts/:id/complete requires ≥1 logged set, COALESCEs completedAt, awards 25 pts once per day (dedupe `workout:<date>`). Completed workout dates count toward the Wellness Streak.
- **Muscle recovery**: GET /workouts/recovery — 72h linear decay from each muscle's last completed training (primary muscle weight 1.0, secondary 0.5, 14-day lookback); returns recoveryPct 0-100 (100 = fresh) per muscle.
- **Progressive overload suggestions**: GET /exercises/:id/suggestion — last completed performance +5 lbs (weighted) or +1 rep (bodyweight); defaults 3×10 when no history.
- **AI generation**: POST /workouts/generate — Grok 4.5 json_object builds a session from preferences (goal/experience/equipment/duration/days + free-text limitations in `<patient_data>`) and current muscle recovery (avoids tired muscles). Zod-clamped (sets 1-6, reps 1-30, weight 0-500, 3-10 exercises), exercise ids validated against the equipment-filtered library (≥3 valid required), 3 generations/day (429; cap rechecked inside per-user in-flight promise so double-taps can't double-burn). Doctor-deferral language; page shows a static "not medical advice — stop if anything hurts, ask Dr. Copley" disclaimer.
- **Web UI**: `pages/workouts.tsx` + `components/workouts/` — Today/Recovery/Library tabs, history list, detail view with per-exercise set logging + suggestion hints, add-exercise dialog (reuses library), preferences dialog.
