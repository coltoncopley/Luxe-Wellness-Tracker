## Retention features (2026-07)

- **Wellness Streak** (Home card): GET /streak counts consecutive days with any qualifying log (food, weight, glow, mind, activity), computed live from distinct log dates — no streak table. Grace: today not yet counted doesn't break the streak. Once-ever milestones (7/14/30/60/100 days → 50/75/150/300/500 pts) awarded via reward_events dedupe `streak:<days>` (survives streak resets). Response includes current, longest, todayCounted, nextMilestone.
- **My Journey `/journey`**: GET /journey read-only recap timeline — weight trend, milestones, monthly summaries, progress photo references. Patient-private.
- **Weekly Report `/weekly-report`**: GET /weekly-report lazily generates an AI recap of LAST week (Mon-Sun ET) on first request, cached in `weekly_reports` (unique user+week, onConflictDoNothing, per-user in-flight map). Wins/focus/encouragement from the patient's own stats; educational-only language.
- **Monthly community challenges** (Community page section): `challenges` + `challenge_participants` tables; lazy ensureChallenges seeds current+next month from a rotating template list (log_days/meals/glow_checkins/weigh_ins/move metrics). GET /community/challenges + POST /community/challenges/:id/join. Progress computed from the user's OWN logs only — only aggregate participant/completion counts shared ("only you can see this" copy). Completion awards 150 pts, dedupe `challenge:<key>:<month>`.
- **Meal Plan `/meal-plan`**: endpoints `/meal-plan/current` (GET), `/generate` (POST), `/preferences` (GET/PUT), `/meal/suggest` (POST), `/meal/apply` (POST), `/meal/recipe` (POST), `/people` (PATCH), `/shopping-list/check` (PATCH), `/shopping-list/email` (POST). AI 7-day plan (Grok 4.5 json_object, 90s timeout, Zod-validated: exactly 7 days, calories clamped 0-2500, dates assigned server-side; each meal carries an `ingredients[]` list — name/quantity/unit/category, capped 8/meal, from which the shopping/grocery list is derived server-side) built from goal facts + 30 distinct recent food names AND explicit preferences (see below) in a `<patient_data>` data-not-instructions block. Stored in `meal_plans` (jsonb content, unique user+week). Max 2 generations per ET week — generation AND upsert share one in-flight promise per user (double-tap burns one generation), setWhere generations<2 race-loss → 429 ("fresh plan unlocks Monday"), AI failure → 503 and never burns quota.
  - **Preferences** (`meal_plan_preferences` table, one row/user): `allergies[]` (always avoided), `dislikes[]` (foods to skip), `dietStyle` (free text, e.g. "vegetarian"), plus a `people` count (1–20, mirrored on the plan for scaling) and an append-only `avoidDishes[]` learned from swaps (dishes the patient removed). All fed into every generate + suggest prompt.
  - **Per-meal swap** (`/meal/suggest` → `/meal/apply`): remove a meal → Grok returns 3 fresh alternatives (transient `pending_suggestions` on the plan, keyed by date+mealType) → patient picks one → applied in place; **only on that confirmed pick** is the removed dish name appended to `avoidDishes` so future plans/suggestions skip it (opening the swap and canceling without picking learns nothing). Rate-limited to 10 swaps/ET day (`suggest_count`/`suggest_date`); AI failure → 503, never burns quota; expired/stale suggestion set → 409.
  - **Shopping list** (`shoppingList` — aggregated from meal `ingredients[]` by name|unit, summed × `people`, rounded to 0.25, units never converted; categories Produce/Protein/Dairy/Grains/Pantry/Frozen/Other). Legacy names-only `grocery` kept for back-compat. Per-item check-off persisted in `meal_plan_grocery_checks` (`/shopping-list/check`, keyed by stable `itemKey`; checks cleared on regen, kept on meal swap). `/shopping-list/email` sends the list to the account email (Resend, 5/day in-memory limit); web/mobile also offer native Share / clipboard.
  - **Shop handoff (2026-07)**: per-meal opt-out + Instacart. `meal_plan_meal_excludes` table (row = meal excluded from shopping; unique user+week+date+mealType; cleared on regenerate, kept on swap; part of the DELETE /me chain). `PATCH /meal-plan/meal/shop` {date, mealType, shop} toggles it (404 if date not in this week's plan); excluded slots are skipped when deriving `shoppingList`, and for ingredient-complete plans the legacy `grocery` now always mirrors the scaled list (so shipped mobile binaries respect opt-outs too). Plan response carries `excludedMeals[]` + `instacartEnabled`. `POST /meal-plan/shopping-list/link` {items[]≤200} calls the Instacart Developer Platform `products_link` API (Bearer `INSTACART_API_KEY`; base URL `INSTACART_API_URL` override, else connect.dev.instacart.tools in dev / connect.instacart.com in production — production needs Instacart's free key approval). Units mapped to IDP vocabulary (g→gram, oz→ounce, lb→pound, ml→milliliter; cup/tbsp/tsp/can/bunch pass through; clove/slice/item→each with the original measure in `display_text`). 20 links/user/ET-day in-memory limit, 15s abort timeout, generated URLs cached by payload hash, 503 with generic copy on Instacart failure (details only in server logs). UI: "Shop" button on the shopping list (web dialog `ShopDialog`, mobile full-screen `ShopModal`) preselects still-needed (unchecked) items with per-item checkboxes → "Open in Instacart" (rendered only when `instacartEnabled`; store choice incl. Walmart happens inside Instacart) + Copy (web) / Share (mobile) fallback; cart icon on every meal card toggles that meal's inclusion (testids `toggle-shop-<date>-<mealType>`, `button-shop-list`).
  - **Kroger cart + Walmart links (2026-07)**: Instacart paused new partner signups, so the Shop dialog gained direct options. Walmart: every item row is a `walmart.com/search?q=<name>` link (Walmart has no public add-to-cart API; testid `link-walmart-<itemKey>`, mobile uses a Feather external-link icon). Kroger: per-member OAuth against the free Kroger Public API (scopes `product.compact cart.basic:write`; covers Ralphs, Fred Meyer, King Soopers, Smith's, Fry's, Harris Teeter, QFC…). `kroger_tokens` table (user-unique access/refresh/expires_at; in the DELETE /me chain). `GET /kroger/status` {enabled, connected} drives all UI visibility; `GET /kroger/connect-url?platform=web|mobile` returns the authorize URL carrying an HMAC-signed state (SESSION_SECRET-keyed, 10-min expiry, timingSafeEqual) so the PUBLIC `GET /kroger/callback` — mounted before the auth gates because mobile returns in a bare system browser with no session — can identify the member; web → redirect `/meal-plan?kroger=connected|error` (page strips the param, toasts, reopens the dialog), mobile → a small "return to the app" page (ShopModal refetches status on AppState active). `POST /kroger/cart` {items:[{name}]≤60} searches each name (`GET /v1/products?filter.term`, concurrency 4, first UPC) then one `PUT /v1/cart/add` (qty 1 each — the cart API is write-only, members adjust quantities on kroger.com/cart) → {added[], missed[], cartUrl}; a failed refresh or 401/403 deletes the token row and 409s so clients flip back to "Connect Kroger"; 30 sends/user/ET-day in-memory. Dormant until `KROGER_CLIENT_ID` + `KROGER_CLIENT_SECRET` are set; production additionally needs `KROGER_REDIRECT_URI` and both dev + prod `/api/kroger/callback` URLs registered in the Kroger developer portal. Buttons: `button-connect-kroger` / `button-send-kroger` (web dialog footer).
  - **Recipes** (`/meal-plan/meal/recipe` POST): tap any meal → AI-written step-by-step cooking guide (Grok 4.5, 60s timeout, 3–12 steps Zod-validated; steps deliberately amount-free — quantities come from `ingredients[]` scaled by `people`), cached permanently in the plan's jsonb content (swap/regenerate drops it). Response carries pre-scaled `ingredientLines`. In-flight dedupe keyed user+slot+dish name so a mid-flight swap never attaches a stale recipe; no extra rate counter (bounded by 28 slots + swap limits). Web: dialog; mobile: bottom-sheet modal.
  - **Ingredient backfill**: plans generated before the shopping-list overhaul lack `ingredients[]`, so their list showed names only. `GET /meal-plan/current` fire-and-forgets an AI backfill (in-flight deduped, ≥10 min retry gap, re-reads row and skips slots swapped mid-flight, aborts if plan regenerated, never burns a generation) — the list gains scalable quantities on the next fetch. A recipe request on such a meal also backfills that meal's ingredients.
  - Patient-private, premium-gated, disclaimer footer. Both web (`pages/meal-plan.tsx`) and mobile (`app/explore/meal-plan.tsx`) have full parity: preferences dialog, per-meal swap, servings stepper, checkable list, email + share.

## Workouts `/workouts` (2026-07)

- Fitbod-style training suite, routes in `routes/workouts.ts`, schema in `lib/db/src/schema/workouts.ts` (5 tables: `exercises`, `workouts`, `workout_exercises`, `workout_sets`, `workout_preferences`). Premium-gated + requireAuth (NOT patient-only — staff may self-track). All data user_id-scoped, patient-private.
- **Exercise library**: 99 seeded exercises (14 muscle groups, 7 equipment types, difficulty levels, instructions, primary + secondary muscles). GET /exercises; seeded idempotently via `seedExercises` (also runs in prod self-seed).
- **Custom lifts (patient-added, private) (2026-07)**: a patient can add their OWN exercise, private to just them, then use it in workouts + set logging exactly like a library exercise. Mirrors the "custom restaurants" pattern. Schema: nullable `exercises.owner_user_id` (NULL = shared library; set = that user's private lift) + two partial unique indexes on `lower(name)` — one `WHERE owner_user_id IS NULL` (library names stay globally unique) and one per-owner (a user can't dupe their own names, but their name can coexist with a library/other-user name). `visibleExercises(userId)` = `owner_user_id IS NULL OR owner_user_id = userId`; every exercise-id lookup used for workouts/sets/suggestions/name-dup checks is scoped through it, so custom lifts are accepted where library ones are and never leak across users. `GET /exercises` returns library + the caller's own customs, each own row flagged `isMine=true` (ownerUserId itself is never serialized). `POST /exercises/custom` (`CustomExerciseInput`: name required, primaryMuscle/equipment required, secondaryMuscles/difficulty/instructions optional) creates the lift and auto-finds a how-to demo video (~8s budget; falls back to the permanent YouTube-search link when none is found); rate-limited MAX 50 total lifts/user + 10/day (429). `DELETE /exercises/{id}` is owner-only (coarse **404** for non-owners / IDOR, never revealing existence) and returns **409** if the lift is referenced by any `workout_exercises` row (can't delete an in-use lift). AI generation's candidate pool stays library-only (`owner_user_id IS NULL`) by design. Web: "Add your own lift" button + `AddCustomLiftDialog.tsx` in the Library tab; own lifts show a "Mine" badge and a trash-delete with confirm dialog. Mobile: parity in `app/explore/workouts.tsx` (`CreateCustomLiftModal`, "Mine" pill, Alert-confirm delete).
- **Workouts CRUD**: create (date + title), list (exercise/set counts), detail, delete; add/remove exercises; log/delete sets (reps + optional weightLbs). POST /workouts/:id/complete requires ≥1 logged set, COALESCEs completedAt, awards 25 pts once per day (dedupe `workout:<date>`). Completed workout dates count toward the Wellness Streak.
- **Auto-mirror to Activity (2026-07)**: completing a workout also logs a `strength` entry into the `activities` table (source=`workout`, externalId=`workout:<id>`, notes=workout title, durationMin estimated from set count clamped 10–120) so strength training appears in the Activity & Sleep "Move" log alongside walks/runs and counts toward Active-minutes totals. Best-effort (try/catch, never fails completion), idempotent via the partial unique index (userId, source, externalId) so re-completing can't duplicate, and awards NO extra points (completion already awards them). Deleting the workout removes the mirrored activity. Source can't be forged from the client (POST /activities whitelists fields; no `source` on `ActivityInput`). Workout-sourced entries aren't user-deletable from the activity list (consistent with Oura/phone-synced entries); they render a "Workout" source badge on web + mobile.
- **Muscle recovery**: GET /workouts/recovery — 72h linear decay from each muscle's last completed training (primary muscle weight 1.0, secondary 0.5, 14-day lookback); returns recoveryPct 0-100 (100 = fresh) per muscle.
- **Progressive overload suggestions**: GET /exercises/:id/suggestion — last completed performance +5 lbs (weighted) or +1 rep (bodyweight); defaults 3×10 when no history.
- **AI generation**: POST /workouts/generate — Grok 4.5 json_object builds a session from preferences (goal/experience/equipment/duration/days + free-text limitations in `<patient_data>`) and current muscle recovery (avoids tired muscles). Zod-clamped (sets 1-6, reps 1-30, weight 0-500, 3-10 exercises), exercise ids validated against the equipment-filtered library (≥3 valid required), 3 generations/day (429; cap rechecked inside per-user in-flight promise so double-taps can't double-burn). Doctor-deferral language; page shows a static "not medical advice — stop if anything hurts, ask Dr. Copley" disclaimer.
- **Pre-generation questionnaire (2026-07)**: POST /workouts/generate takes an OPTIONAL `GenerateWorkoutInput` body (all fields optional; empty/absent body = default behavior, unchanged) — `focusAreas` (array of body-area enums, multi-select — server unions + de-dupes each area's muscles via `FOCUS_AREAS`; `full_body`/unknown entries filtered out; empty/absent = no restriction), `durationMins` (10-120, overrides saved `targetDurationMins`), `energy` (low/medium/high → `ENERGY_GUIDANCE` prompt block), `avoidToday` (≤300 chars free-text, trimmed + capped server-side, merged with saved limitations inside `<patient_data>` as data-not-instructions). Params are transient per-generation — no new DB tables/columns. Invalid values 400 before consuming a generation. Surfaced as a short questionnaire shown BEFORE generation (web `GenerateWorkoutDialog.tsx`, mobile questionnaire ModalShell).
- **"Watch how-to" embedded video player (2026-07)**: per-exercise button opens a built-in player showing a curated YouTube demo. No API key — one video was hand-curated + embeddability-verified per exercise, baked into `lib/db/src/exercise-videos.ts` (`EXERCISE_VIDEO_IDS`, keyed by exercise name) and seeded onto `exercises.how_to_video_id` via `.onConflictDoUpdate` on `exercisesTable.name` (backfills existing rows). Exposed as `Exercise.howToVideoId` (optional + nullable) through the OpenAPI/Zod contract on both `GET /exercises` and workout-detail.
  - Player mounts the embed only while open, using privacy-friendly `youtube-nocookie.com/embed/<id>` (web: `referrerPolicy=strict-origin-when-cross-origin`).
  - A **permanent YouTube-search fallback** (`howToVideoUrl()` → `youtube.com/results?search_query=<exercise> how to form`) is always shown beneath the player, and is used directly (no player) when an exercise has no curated `howToVideoId`. This covers videos that later get pulled or have embedding disabled.
  - Web: shared `components/workouts/HowToVideo.tsx` (shadcn Dialog; `variant="button"` in LibraryTab expanded card, `variant="link"` in WorkoutDetailView exercise block). Mobile: shared `components/HowToVideo.tsx` (RN Modal) with a platform-file split — `HowToVideoPlayer.native.tsx` renders a `react-native-webview` WebView; `HowToVideoPlayer.tsx` renders a DOM `<iframe>` (Expo web + TS resolution), so the native module never enters the web bundle. Labels/options shared in `components/workouts/labels.ts`.
  - **Deploy caveat:** `react-native-webview` is a native module absent from any already-shipped App Store binary — the next mobile release must be a full native EAS build; do not push an OTA/EAS Update containing this JS to an old binary (the player would crash with "module not found"). Expo Go and Expo web are unaffected.
- **Web UI**: `pages/workouts.tsx` + `components/workouts/` — Today/Recovery/Library tabs, history list, detail view with per-exercise set logging + suggestion hints, add-exercise dialog (reuses library), preferences dialog, generate questionnaire dialog.
